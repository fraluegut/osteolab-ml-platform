ArqueoBytes presenta

OsteoLab

Clasificación automática de restos óseos a partir de una foto. Combinamos medición geométrica clásica con visión por computador y deep learning para identificar el grupo morfológico de un hueso — cráneo, vértebra, hueso largo, pelvis y más — en segundos.

Probar con una foto Cómo funciona
9 grupos morfológicos
~78% balanced accuracy sobre fotos reales†
2 señales combinadas: forma + textura

†Modelo híbrido, banco de 57 fotos reales nunca vistas en entrenamiento (detalle abajo). Usamos balanced accuracy en vez de accuracy plana porque con el desbalance de clases del dataset (8.5× entre el grupo más y menos representado) la accuracy puede quedar bien aunque el modelo falle sistemáticamente en varias clases — ver ejemplo real en "Resultados".

El proyecto

De la foto al grupo morfológico

OsteoLab nació como una herramienta de apoyo para catalogar restos óseos sin depender de que un especialista esté siempre disponible para una primera identificación. El proceso hasta el modelo actual fue iterativo — cada etapa respondió a una limitación real encontrada en la anterior.

  1. 1

    Medición geométrica clásica

    El punto de partida fue puramente visión por computador: localizar el contorno del hueso con OpenCV y extraer medidas relativas — proporción de aspecto, elongación, circularidad, solidez, convexidad, perfil de anchura a lo largo del hueso y momentos de Hu. Sobre ese vector de medidas se entrenó un RandomForestClassifier por grupo morfológico.

  2. 2

    Filtrar antes de clasificar

    Antes de invertir cómputo en medir y clasificar, la imagen pasa por un filtro CLIP zero-shot (¿esto es un hueso?) y un filtro binario ResNet18 de refuerzo. Así se descartan fotos que no contienen huesos sin necesidad de dataset propio para esa tarea.

  3. 3

    Pocos huesos reales, muchos renders sintéticos

    Con uno o dos especímenes reales por hueso concreto, el modelo no puede generalizar a nivel de especie o pieza exacta — por eso se agrupa por forma general (grupo morfológico) y se amplía el dataset con renders 3D sintéticos con ruido. La síntesis pasó por varias iteraciones: ruido clásico primero, y más adelante migración a BlenderProc (máscaras exactas, HDRIs reales de fondo, suciedad procedural, óptica variable) — combinando ambos enfoques en vez de sustituir uno por otro, que fue lo que mejor resultado dio.

  4. 4

    El hueco entre síntesis y realidad

    El banco de evaluación con renders limpios llegó a acertar por encima del 77%, pero las fotos reales rondaban solo el 27%. El extractor geométrico descarta toda la textura y el sombreado de la imagen — señal que sí podía ayudar a cerrar ese hueco.

  5. 5

    Entra la CNN: modelo híbrido

    Se entrenó un backbone ResNet18 preentrenado en dos fases (cabeza congelada primero, luego ajuste fino completo a tasa de aprendizaje baja) en dos variantes: una CNN pura sobre píxeles, y un modelo híbrido que concatena el embedding de la CNN con el mismo vector de medidas geométricas antes de una cabeza de clasificación — la apuesta era que forma y textura son señales complementarias, no redundantes. Los resultados confirmaron la apuesta: el híbrido superó a ambas ramas por separado en todos los bancos de prueba.

  6. 6

    La segmentación importaba más de lo esperado

    Sustituir la segmentación clásica (umbralización tipo Otsu) por Grounded-SAM — segmentación guiada por lenguaje natural — mejoró de forma notable tanto el modelo geométrico como el híbrido. La medición era buena; lo que fallaba antes era encontrar el hueso dentro de la imagen.

  7. 7

    12 fotos reales, el mayor salto

    Incorporar apenas 12 fotografías reales al entrenamiento — un 0.3% del dataset combinado — movió más el resultado que cualquier mejora de síntesis probada hasta entonces. El hueco de dominio entre sintético y real se cierra, sobre todo, con datos reales de verdad.

Los datos

De la malla 3D a la fila de entrenamiento

Cada fila que ve un modelo empieza como un espécimen 3D catalogado, pasa por un render multi-vista con ruido sintético y, en un puñado de casos, se cruza con una fotografía real aceptada tras revisión manual. Así queda el recuento actual.

Catálogo de mallas 3D

122 especímenes descargados
11 especies distintas (mayoría Homo sapiens, resto primates de referencia)
21 → 9 huesos objetivo, agrupados en 9 grupos morfológicos
3 fuentes: Sketchfab (80 esp.), MorphoSource (27 esp.), Smithsonian (7 esp.)

De malla a imagen

Cada espécimen se renderiza desde 24 ángulos fijos. Ese render limpio (2419 vistas) se combina con dos variantes de ruido sintético — clásico y BlenderProc (máscaras exactas, HDRIs reales, suciedad procedural) — para formar el dataset combinado con el que se entrena el modelo actual: 3855 filas, 122 especímenes, 12 especies.

1. Espécimen catalogado — Human Femur, escaneado por el laboratorio de anatomía de Eric Bauer (Elon University). CC Attribution. Ver en Sketchfab ↗

2. Render limpio — una de las 24 vistas fijas generadas en Blender a partir de la malla, sin ruido ni fondo.

3. + fondo real — el render (RGBA) se compone sobre una foto real de data/backgrounds/ (mesa, tierra, mármol, tela...) para que el modelo no aprenda a depender del fondo blanco de estudio.

4. Variante BlenderProc — pipeline alternativo con HDRI real, suciedad procedural y máscara ground-truth exacta exportada de la geometría.

Resultados

Rendimiento sobre fotos reales

El examen que de verdad importa no es el banco de renders limpios (optimista, porque comparte distribución con el entrenamiento) sino un banco aparte de fotografías reales de huesos, nunca vistas por ningún modelo. Esta tabla compara los cuatro enfoques probados, antes y después de sumar fotos reales al entrenamiento.

Modelo Descripción Accuracy · solo síntesis histórico Accuracy · + fotos reales re-verificado hoy
Geométrico RandomForest sobre medidas OpenCV 0.5185 0.5439
CNN ResNet18 sobre píxeles del recorte segmentado 0.5741 0.6842
Híbridomejor modelo CNN + medidas geométricas concatenadas 0.6852 0.7719
Cascada Regla de elongación → hueso largo; resto → híbrido 0.6296 0.7719

Columna "solo síntesis": accuracy histórica, checkpoint anterior a sumar fotos reales al entrenamiento — no re-verificada (haría falta reentrenar esa variante para tener también su macro-F1/balanced accuracy). Columna "+ fotos reales": re-ejecutada hoy contra los modelos y el banco actuales (57 de las 63 fotos del manifest — 6 no están ya en disco, ver nota abajo), por eso difiere un poco del número citado en versiones anteriores de esta página. Cascada sale idéntica al híbrido en este banco: la regla de elongación solo se disparó en 8 fotos, y en las 8 coincidió con lo que la CNN ya predecía sola.

Accuracy esconde el desbalance — por eso el titular usa balanced accuracy

Con 8.5× de diferencia entre el grupo más y menos representado, un accuracy alto puede convivir con una clase entera en 0% de recall (pasa exactamente con "costilla" en el modelo geométrico, abajo). Balanced accuracy y macro-F1 promedian por clase antes de promediar entre clases, así que una clase ignorada pesa igual que una que domina el dataset — no se puede compensar acertando mucho en las clases fáciles.

Todas las cifras de esta tabla se generaron en la misma corrida, hoy, contra el mismo banco de 57 fotos reales (training/evaluate_cnn_real_photos.py / evaluate_real_photos.py / evaluate_cascade_real_photos.py, segmentación Grounded-SAM). El híbrido pasa de 0.772 accuracy a 0.783 balanced accuracy — sube, no baja: en este banco concreto no hay ninguna clase con recall en 0 para el híbrido (ver desglose completo abajo), así que balanced accuracy no lo penaliza. El geométrico sí lo sufre: 0.544 accuracy pero 0.47 de macro-F1, arrastrado por "costilla" en 0.00 precisión/recall/F1.

Infraestructura

De qué partes está hecho OsteoLab

El repo separa entrenamiento, servicio al usuario, código compartido y orquestación en carpetas independientes. ./run.sh levanta el stack completo con Docker Compose; cada pieza también puede correr suelta.

Servicios (con URL de acceso)

🚀 API backend FastAPI Inferencia + web de producto (/classify, /hybrid/classify, /pca/reference...). http://localhost:8000 serving/backend/ 🎛️ UI Streamlit demo Pipeline paso a paso: sube imagen → CLIP → medir + clasificar → PCA. http://localhost:8501 serving/frontend/ 📊 MLflow tracking Experimentos, métricas y modelos registrados de cada entrenamiento. http://localhost:5000 mlops/docker/
🐘 PostgreSQL interno Backend de almacenamiento de MLflow. Sin UI propia. postgres:5432 (solo red interna de Docker) mlops/docker/docker-compose.yml

Código y pipeline (sin servicio propio)

🧠 training/ CLI Entrena y evalúa los 3 modelos (geométrico, CNN, híbrido). python -m training.train_geometric
🧩 shared/ librería Código compartido entre training y serving: filtros CLIP/ResNet18, extracción de features (OpenCV) e inferencia. importado como shared.*, no se ejecuta solo
🐳 mlops/docker/ Docker Dockerfiles + docker-compose.yml: orquesta postgres, mlflow, API y UI. ./run.sh
🌬️ mlops/airflow/ no desplegado DAG de orquestación del pipeline de entrenamiento. Todavía no forma parte de docker-compose.yml. mlops/airflow/dags/train_pipeline.py
🗂️ DVC CLI Versiona datos y pipeline reproducible de entrenamiento. dvc repro · dvc status

Ampliar base de datos

Pega una URL de Sketchfab

Si el modelo trae los huesos como objetos separados (p. ej. un esqueleto "desplegado"), cada uno se descarga, se separa y se renderiza por su cuenta. El nombre que le puso el autor (l_femur, c3...) se intenta mapear al grupo morfológico automáticamente; lo que no se reconoce con confianza pasa a Identificación Manual.

Ninguna imagen se guarda de forma permanente.
